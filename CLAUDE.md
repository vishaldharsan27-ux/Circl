# Circl

Flutter app for real-time proximity-based and interest-graph matching — discover and connect with nearby people who share your AI/ML interests to build or learn projects together, updated live as people move or interests change. College project (Sri Shakthi Institute); needs a demoable prototype.

## Stack

- **Frontend**: Flutter (`lib/`). Key packages: `provider` (state), `http`, `socket_io_client`, `geolocator`, `shared_preferences`, `jwt_decoder`, `google_fonts`, `flutter_animate`.
- **Backend**: Node/Express + Socket.IO on one HTTP server (`backend/server.js`), MongoDB via Mongoose (Atlas, `.env` → `MONGO_URI`). Serves the compiled Flutter web build as static files so the app and API share one origin — lets the whole thing be demoed over a single ngrok URL (`network_config.dart` mirrors `Uri.base` on web, resolves to `10.0.2.2:5000`/`localhost:5000` on native unless `--dart-define=BACKEND_ORIGIN=...` is passed).
- No commits yet as of 2026-08-06 — everything was uncommitted working-tree state on `develop`.

## Conventions

- Screens/widgets: dark theme by default (user-toggleable to light, see below), `#0D0D0D`/`#F5F5F7` background, `#1A1A1A`/white cards, `#00E676` accent (same in both modes), `GoogleFonts.poppins`, 16px rounded corners. Match this exactly in new UI — **never hardcode `Color(0xFF0D0D0D)`/`Color(0xFF1A1A1A)`/`Colors.white*` for backgrounds, cards, or text in a new screen; use `lib/theme/app_colors.dart`'s `AppColors.background/card/textPrimary/textSecondary/textMuted/textFaint/divider/subtleFill(context)` helpers instead** so it respects the active theme. The accent green (`Color(0xFF00E676)`) is the one color that's fine to hardcode — it's identical in both themes.
- State: one `ChangeNotifier` provider per domain (`AuthProvider`, `UsersProvider`, ...), each wrapping a plain service class (`ApiService`, `AuthService`, `SocketService`) — providers hold UI state (`isLoading`, `errorMessage`) and call services; services do the actual HTTP/socket work and know nothing about Flutter widgets.
- Backend routes: one router per domain (`routes/auth.js`, `routes/users.js`), `authMiddleware` on anything user-scoped, plain functions at the top of the route file for pure logic (e.g. matching/distance math) rather than inline in handlers.

## Status by feature area (as of 2026-08-06)

- **Auth** — Done. Register/login, JWT (30d), bcrypt, auto-login via stored token.
- **Proximity/location** — Done for a live version. `Geolocator.getPositionStream()` (10m `distanceFilter`) pushes to `PUT /api/users/location` (throttled ~8s) from `home_screen.dart`; a 20s `Timer.periodic` re-fetches `/nearby` so movement by *other* users shows up without manual refresh. `User.lastLocationAt` tracks freshness (not yet used to filter `/nearby` — deliberately, to avoid silently hiding stale demo accounts).
- **Interest matching** — Done for a scoped "interest graph", retagged 2026-09-30 from a generic lifestyle taxonomy to an AI/ML-specific one (the app's premise is now "find nearby people to build or learn AI/ML projects with," not general hobby overlap — went through an intermediate general-engineering taxonomy first before narrowing to AI/ML specifically, same day). `backend/utils/interestGraph.js` models 12 tags — Gen AI, LLM, SLM (category `GenAI`); Agentic AI, RAG, LangChain (`Applied AI`); Machine Learning, Deep Learning, Computer Vision (`Core ML`); MLOps, Data Engineering, Cloud/DevOps (`MLOps`) — as leaves under those 4 category nodes, and computes `matchPercent = round(100*(0.7*tagJaccard + 0.3*categoryJaccard))` — symmetric, unlike the old flat formula. Same tag list is duplicated as a static `_allInterests` array in `interest_screen.dart` and `profile_screen.dart` (no shared constant file yet). `UserModel.relatedInterests` + a third amber chip state in `user_card.dart` visualize category-level (non-exact) matches. Not a graph DB — a static category map, by design.
- **Real-time/sockets** — Done for the core loop, with a known limitation. Backend emits `connection_request`/`connection_accepted`; client listens for both via `ConnectionsProvider` + `RequestsScreen` (accept/reject UI, inbox badge). `GET /api/users/requests/incoming` covers requests received while offline. **No equivalent catch-up exists for the sender** — if your socket isn't live at the exact moment someone accepts, you miss the toast (confirmed via server log: a disconnected client never got `connection_accepted`). Mitigated, not fixed: `GET /nearby` now returns `connectionStatus` ('none'/'pending'/'accepted') per user, computed from the `Connection` collection, and `UserCard` renders "Connect →"/"Request Pending"/"Connected ✓" accordingly — so the existing 20s periodic `/nearby` poll (built for live location) eventually surfaces the accepted state even if the toast was missed. `POST /connect` also now blocks duplicates in both directions and once already `accepted`.
- **Preference matching** — Added 2026-09-30. A second, independent matching axis from interest tags: each user picks one intent — `Build` (wants a project partner), `Learn` (wants to study together), `Mentor` (wants to guide someone), or `Hire` (recruiting for a project) — via `UserModel.preference` (`backend/models/User.js`, enum). `backend/utils/preferenceMatch.js` defines a compatibility map (`Build`↔`Build`/`Hire`, `Learn`↔`Learn`/`Mentor`, symmetric) and `GET /nearby` returns a boolean `preferenceMatch` per user alongside the existing `matchPercent`; `UserCard` renders a "Looking to X" chip, highlighted green when compatible. Picked at onboarding (`interest_screen.dart`) and editable in `profile_screen.dart`, both via `PUT /api/users/profile`.
- **Project pitch + Meet handoff** — Added 2026-09-30. Once a `Connection` is `accepted`, either side can send one text "pitch" (a project idea) to the other via the new `Pitch` model/`routes/pitch.js` (`POST /api/pitch`, one-shot per direction — a second pitch attempt in the same direction is rejected). The recipient accepts/rejects via `PUT /api/pitch/:id/respond`; when **both** directions end up `accepted` (i.e. each side accepted the other's pitch), the backend emits `pitch_matched` to both sockets. `lib/screens/pitch_screen.dart` (reached from `UserCard`'s "Connected ✓ · Pitch Project →" button) drives this and then unlocks a Meet-handoff section. **The Meet link is not auto-generated** — there's no Google Cloud OAuth app in this project, so it's a manual relay by design: one user taps "Create Google Meet" (opens `meet.google.com/new`, which creates an instant meeting under their own Google login), pastes the resulting URL back into the app, and `POST /api/pitch/meet/share` relays it to the other user over socket (`meet_link_shared`) with no server-side persistence. Revisit only if real Calendar API credentials get set up later.
- **Projects dashboard** — Added 2026-09-30. Lets a user group their *own* accepted connections into named "projects" (e.g. working on different things with different people) — this is a personal organizer, not a shared/multi-user object: only the owner sees and edits their `Project` docs (`backend/models/Project.js`: `owner`, `name`, `memberIds[]`), and `memberIds` is restricted server-side to connections that are `accepted` between the owner and each member (`assertAcceptedConnections` in `routes/projects.js`). Full CRUD at `/api/projects` (+ `GET /api/users/connections/accepted` to list pickable people). `lib/screens/dashboard_screen.dart` — reached via a new dashboard icon in `home_screen.dart`'s `AppBar` — renders a fixed-width left sidebar listing projects (tap to select, "+" to create) next to a detail pane (members list, rename, delete, "Manage Members" bottom sheet). Independent of the pitch/Meet feature — a project here is just a label over a set of people, not tied to any pitch or match.
- **GitHub push tracking per project** — Added 2026-09-30. Each `Project` can optionally link a public GitHub repo (`Project.repoUrl`, validated as a `github.com/owner/repo` URL by `backend/utils/github.js`'s `parseGithubRepoUrl`). **Important constraint, not a bug**: this only ever shows *pushes* — git has no server-side concept of a "pull" (it's a local fetch+merge that never touches GitHub), so there is no API or webhook for it anywhere, in this app or otherwise. `GET /api/projects/:id/commits` calls GitHub's public unauthenticated commits API (`fetchRecentCommits` in `utils/github.js`, via Node's native `fetch`) and returns the last 20 commits (sha/message/author/avatar/date) — no GitHub token, so **public repos only**; a private repo 404s with a clear message. Refresh is manual (a button, via `ProjectsProvider.fetchCommits`) rather than background polling, both to stay within GitHub's 60 req/hr unauthenticated rate limit and to avoid a recurring job no one's watching. `dashboard_screen.dart`'s project detail pane got a "Repository" section (link/change repo, refresh button, commit feed) below the existing members section.
- **Day/night mode** — Added 2026-10-01. `ThemeProvider` (`lib/providers/theme_provider.dart`) holds a `ThemeMode` persisted to `SharedPreferences` (key `isDarkMode`, defaults to dark so existing behavior is unchanged for anyone who doesn't touch the toggle); `main.dart` wires `theme`/`darkTheme`/`themeMode` on `MaterialApp` from it. All 11 screens/widgets that previously hardcoded the dark palette inline (`Color(0xFF0D0D0D)`, `Color(0xFF1A1A1A)`, `Colors.white70` etc.) now go through `lib/theme/app_colors.dart`'s context-aware `AppColors` helpers instead — the only hardcoded palette values left in `lib/` are inside `app_colors.dart` itself and the two `ThemeData` builders in `main.dart`. Toggle lives in `profile_screen.dart` as a `SwitchListTile` ("Dark Mode"). The light palette mirrors the dark one structurally (white cards instead of `#1A1A1A`, `#F5F5F7` background instead of `#0D0D0D`, black-based text opacities instead of white-based) but the accent green is unchanged in both.
- **My Connections list** — Added 2026-10-01. A dedicated screen (`lib/screens/my_connections_screen.dart`, reached via a people-icon button in `home_screen.dart`'s `AppBar`) listing every accepted connection regardless of current proximity — the nearby feed only shows people currently in range, so this is the first place to see *everyone* you've connected with. Reuses the existing `GET /api/users/connections/accepted` endpoint (originally built for the dashboard's project-member picker); `ConnectionsProvider` gained `acceptedConnections`/`fetchAcceptedConnections()` alongside its existing incoming-requests state, since both are "my connections" domain state. Tapping a person opens `PitchScreen` directly — that's the existing one-shot pitch exchange, serving as this app's closest thing to a chat.
- **UI/screens** — Done: Splash → Register/Login → Interest pick (incl. preference) → Home (nearby list, live location, inbox badge, connections icon, dashboard icon) → Requests (accept/reject) → My Connections (full list, tap-to-pitch) → Profile (incl. preference, dark-mode toggle) → Pitch (per accepted connection) → Dashboard (projects, left sidebar, linked-repo commit feed). All screens support light/dark mode.
- **Backend/data layer** — Done: core CRUD + geospatial query + Socket.IO room-per-user pattern + location-push endpoint + interest-graph matching module + preference-compatibility module + Pitch model/routes + Project model/routes + GitHub public-commits integration.
- **Testing** — Still missing beyond the default Flutter widget-test placeholder and ad-hoc `node -e` sanity checks of `interestGraph.js`/`preferenceMatch.js` (not committed test files).
